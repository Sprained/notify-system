# Decisões — notify-system

Registro de decisões tomadas ao longo do projeto, com o porquê. Complementa o
`NOTIFY.md` (que trata do desenho geral) — aqui entram decisões pontuais que
vão surgindo durante a implementação.

| Decisão | Racional |
| --- | --- |
| Telegram: texto puro, sem `parse_mode` | Corpo é arbitrário (curl de qualquer script); `MarkdownV2` exige escapar 18 caracteres — um erro quebra o envio inteiro com `400`. `Markdown` legado escapa só 4, mas formatação é limitada e não compensa o risco pra conteúdo não controlado |
| `click_url` vira inline keyboard button, não link em Markdown | Evita depender de escaping de texto pra formar link — campo separado da API do Telegram |
| Corpo do Telegram > 4096 caracteres (limite da API) trunca e envia | Prioriza entrega parcial sobre rejeitar a notificação inteira |
| Corpo vazio na ingestão (`POST /:topico`) é rejeitado | Notificação sem conteúdo não faz sentido no fluxo |
| `X-Priority` numérico fora do range (1–5) clampa pro mais próximo; não-numérico rejeita `400` | Erro de digitação vira erro claro (`400`); valor fora do range é tolerado pra não quebrar scripts existentes |
| Retry do worker: 1 tentativa inicial + 3 retries (4 tentativas no total), backoff 1s → 2s → 4s entre elas | Cobre falhas transitórias de rede sem segurar o worker por muito tempo nem desistir cedo demais |
| Migração de schema via `golang-migrate` | Padrão de mercado, suporta up/down versionado; custo de aprender agora compensa pra currículo/prática real |
| Testes de integração com banco via `testcontainers-go` | Container Postgres efêmero por execução de teste — não depende de lembrar de subir o `docker-compose.yml` antes de rodar `go test` |
| Driver de Postgres: `jackc/pgx/v5` (não `lib/pq`) | `lib/pq` está em modo de manutenção sem features novas há anos; `pgx` é o que a comunidade Go usa ativamente hoje |
| Roteador HTTP: só `net/http` da standard library (sem `chi`/`gorilla`) | Go 1.22+ já suporta padrão `"POST /{topic}"` com 405 automático em método errado — cobre o que precisamos sem dependência nova |
| `delivery` de subscriber com `kind` sem `Notifier` registrado vira `failed` direto | `last_error` explica que não existe notifier registrado pra aquele kind; falha explícita é melhor que ficar pendente pra sempre sem ninguém perceber |
| Retry do worker roda todo em memória numa única execução; só o resultado final (`sent` ou `failed`) é gravado no banco, não uma escrita por tentativa | Mais simples, sem ganho real de persistir tentativa a tentativa já que o retry inteiro acontece numa chamada síncrona só. Trade-off aceito: se o processo cair no meio do retry, a `delivery` fica em `pending` com `attempts = 0` e reinicia do zero na próxima execução |
| `Worker.ProcessPending` roda em goroutine única dentro do mesmo binário do `cmd/notify` (não processo separado) | Homelab/uso pessoal — mais simples de operar (um processo, um deploy) e o isolamento de processo separado não compensa a complexidade extra aqui |
| Dentro de `ProcessPending`, as `delivery` pendentes são processadas **sequencialmente**, na mesma goroutine — não abre uma goroutine por `delivery` | Simplicidade agora; **trade-off**: se a primeira `delivery` da leva precisar de retry (até 7s de backoff somado), as seguintes da mesma leva esperam ela terminar antes de começar. Anotado aqui pra lembrar de revisitar (processar em paralelo com limite de concorrência) se algum dia isso virar gargalo de verdade — não otimizar antes de sentir o problema |
| Migrations embutidas no binário via `//go:embed migrations/*.sql`, rodadas automaticamente na subida do `cmd/notify` | Bate com a decisão de binário único — não depende de copiar a pasta `migrations/` separado no deploy pro Pi |
| Worker faz polling a cada 10 segundos (`time.Sleep` entre cada `ProcessPending`) | Intervalo arbitrário de partida pra uso pessoal; ajustável depois se precisar de notificação mais rápida |
| `pq.Array(...)` usado só como helper de encode/decode de `TEXT[]` no `Store.Insert`/`Get` (driver continua sendo `pgx`) | Gotcha real descoberto rodando em produção: `pgx` via `database/sql` genérico não decodifica array do Postgres pra `[]string` sozinho — devolve como string crua (`"{a,b}"`), e o `Scan` falha (`unsupported Scan... into *[]string`). `pq.Array` sabe ler/escrever esse formato de texto independente de qual driver está por trás. Esse bug passou batido pelos testes porque nenhum teste testava `Store.Insert`/`Get` com `Tags` preenchida — coberto agora em `TestStore_InsertAndGet_RoundTripsTagsCorrectly` |
| TDD no front só na camada de handler/dados (mesmo padrão do backend); renderização de HTML ganha só smoke test de presença de dado; JS do cliente sem teste automatizado por agora | Testar regra de negócio (filtro de entregas falhadas, dados corretos pro template) tem valor real e reaproveita o padrão já usado em `httpapi`. Testar layout/cor via automação é caro e frágil — validação de visual fica manual/revisão, como já foi feito no mockup aprovado. JS é só troca de aba/toggle por agora, baixo risco — ferramenta de teste JS (Playwright etc.) fica pra quando o front tiver algo mais dinâmico (ex: polling ao vivo), não vale o overhead agora |
| Front renderizado pelo próprio Go: `html/template` + `htmx` (sem SPA, sem build step de JS) | Mantém a filosofia de binário único e stdlib-first já usada no backend. `htmx` resolve a necessidade de "dashboard ao vivo" (contadores, status atualizando) via troca de fragmento HTML, sem exigir API JSON nem framework JS — só 1 arquivo vendorizado embutido via `embed.FS` |
| Testes do pacote `postgres` rodam sequenciais, sem `t.Parallel()` (~80s no total) | Cada teste sobe seu próprio container via `testcontainers-go` — é isso que pesa no tempo, não a query em si. Adicionar `t.Parallel()` nas 21 funções de teste é a melhoria mapeada (Go roda vários containers ao mesmo tempo, limitado por `-parallel`/CPUs), mas fica pendente — aplicar quando o tempo de execução virar um problema de verdade, não antes |
| Botão de submit em formulário grid ganha um `<label>&nbsp;</label>` invisível acima, em vez de tentar alinhar via `justify-content` | Os outros campos têm rótulo + input, então o input começa mais embaixo. O rótulo fantasma (mesma altura dos rótulos reais) garante que o botão nasça exatamente na mesma linha, sem depender de flex/alturas aproximadas. Reaproveitar em qualquer formulário futuro (ex: tela de Assinantes) |
| Template do painel web separa "shell" de "conteúdo" por página (`parsePage` monta `layout.html` + `stats.html` + arquivo da tela, um `*template.Template` por página — não um glob global) | Resolvido na task "Tela: Mensagens". Evita a armadilha do `html/template`: se duas páginas definissem `{{define "content"}}` e fossem parseadas juntas num glob só, uma sobrescreveria a outra silenciosamente, sem erro de compilação. Nav ativo e título do topbar viram dinâmicos via `shellData` (`ActiveNav`, `PageTitle`), que cada tela preenche |
| `POST /:topico` aceita `Content-Type: application/json` com `{"message": "..."}` além do corpo texto puro | Dozzle (webhook nativo de alertas, v10+) manda headers estáticos (`X-Title` etc) + body JSON dinâmico — não dá pra mandar texto puro no body. Detecção por `Content-Type` (`mime.ParseMediaType`, não sniffing do conteúdo) mantém o contrato ntfy-compatible intocado pra quem já manda texto puro via `curl` |
